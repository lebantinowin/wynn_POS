# Wynn's Mart

Owner-operated grocery POS built with Laravel 13.35.0, Livewire 4.4.7 and PostgreSQL 18.4. Products, sale options, stock batches, transactions, customers, supplier balances and cash records now persist in the shared shop database. Browser sessions retain interface state; they no longer own the business records. Desktop/tablet operations and mobile analytics follow the approved Inter/slate/muted-green design. No Node build is required for the current plain CSS interface.

## Run locally

Run `./run-preview.ps1` from PowerShell, then open http://127.0.0.1:8000. PHP requires mbstring, fileinfo and pdo_pgsql. Composer dependencies are installed and locked in composer.lock.

`./setup-postgresql.ps1` creates the dedicated wynn_mart database and wynn_mart_app account after securely prompting for the local postgres administrator password. Windows PowerShell 5.1 automatically launches the installed PowerShell 7 runtime. Generated app credentials stay in the Git-ignored .env; administrator credentials are not saved. Existing database/account names without matching local configuration are not overwritten. A configured installation can rerun the script to verify its connection and apply pending migrations without entering the administrator password again.

The local installation has all eight migrations applied: three Laravel foundation migrations plus POS, offline checkout, shop settings, held carts and the offline recovery audit update. `.env.example` selects PostgreSQL and `POS_STORAGE=database`. File sessions/cache and synchronous queues remain in use. Use migrations against existing records; do not reset a live database with migrate:fresh.

## Owner access

Every shop page and Livewire update requires the single owner account. There is no public registration, default password, staff management or RBAC. Run `./setup-owner.ps1` from the project’s interactive PowerShell terminal to enter the owner name/email and password privately. Passwords require at least 12 characters with mixed case, a number and a symbol; hashing uses Laravel’s configured bcrypt driver. Hidden entry refuses an unprotected terminal fallback, and noninteractive account creation is rejected. The owner occupies reserved user ID 1; account setup cannot replace an existing account, and competing first setups are constrained by the primary key. Other database users cannot access the workspace.

After setup, refresh `/login` and sign in. Successful login rotates the session and returns to the requested page. Failed attempts are limited per email/IP and per IP, with generic credential errors. CSRF protection covers login/logout; sign-out invalidates the session and rotates its token. Sessions expire after the configured 120-minute idle period and use nonpersistent cookies by default. Protected responses prevent caching. Expired Livewire actions are rejected before business logic and return the interface to sign-in.

For local password recovery, run `./setup-owner.ps1 -Reset`. Confirmation is required in the local terminal, and the new password is entered privately. The changed hash invalidates existing device sessions on their next request. Settings shows the owner account and recovery instructions. The implementation is verified, and the owner confirmed successful account setup and login. Android/network access, device registration and HTTPS deployment remain separate work.

## Database backups and recovery

Settings provides Back up now, automatic-backup preferences, recent success/failure history and Check recovery. Defaults are daily backups with 14-day retention; hourly/every-six-hour frequency and 7/30/90-day retention are also available. Pausing automatic backups leaves manual backup available. Archives and metadata stay outside public/signed filesystem routes in Git-ignored `storage/app/backups`.

Backups use PostgreSQL custom-format dumps of the configured application schema, including the owner account. A read-only repeatable-read exported snapshot keeps the archive and saved table fingerprints consistent. SHA-256 checksums, atomic metadata replacement, partial-file cleanup and an exclusive operation lock protect completed copies and prevent overlapping work. Expired registered archives are removed only after a new backup succeeds; failed attempts remain in history. Database passwords are passed only through subprocess environments, and raw tool errors are not exposed in history. Windows subprocesses explicitly retain required system variables for browser and scheduled execution.

`./install-backup-task.ps1` registers a limited Windows task for the current signed-in account. It checks hourly and at sign-in; the application creates a copy only when enabled and due. The task is installed on this computer, and its first scheduled run succeeded. The computer must be on and the account signed in. Run `./run-backups.ps1` for an immediate command-line copy, or add `-Scheduled` to respect the configured interval. `PG_BACKUP_BIN` selects the installed PostgreSQL tools; `PG_BACKUP_SCHEMA` defaults to public.

Check recovery verifies the archive checksum, restores into an isolated temporary PostgreSQL instance on localhost, and compares every saved table and row against the original snapshot fingerprints. It needs no administrator password or elevated database role and never restores over the shop database. The temporary server is stopped and removed afterward; a server that cannot be stopped keeps its files for investigation. `php artisan pos:verify-backup <backup-id>` uses the same check. The actual shop backup passed: 37 tables and 17 records matched. Historical failure attempts from the Windows environment investigation remain visible; the subsequent browser backup and recovery check succeeded.

These are unencrypted database copies. Settings can copy each successful backup to a configured USB/external-drive folder, preserving a matching archive and metadata manifest. The owner chose to configure that folder later, so off-device protection is not yet active. Configuration/application-key and uploaded-file recovery, a controlled production-restore procedure and final recovery objectives remain separate work. Local archives alone do not cover loss of this computer. Pending offline sales use separate browser recovery copies; they are absent from database archives until confirmed.

## Offline checkout

Sign in online, open Shifts & Expenses, then choose **Checkout → Offline checkout → Prepare offline checkout** in the browser that will run Counter 1. Preparation saves the current catalogue, prices, sellable stock and saved customer names. It lasts up to two hours, capped by the configured session lifetime and local midnight. Only one browser can hold the counter; connected business changes pause until that browser synchronizes and finishes. Reports remain available and warn that pending sales are excluded.

The cached `/offline-checkout.html` page supports search/manual barcode entry, individuals/packages, a reloadable cart, cash/change, manually verified GCash/Maya and grocery credit for saved customers. IndexedDB commits each sale, stock deduction, upload event and local receipt together before confirming success. Receipts identify pending uploads; View / reprint and Print / Save PDF retain the original sale. Open/close the drawer and record expenses, loans, repayments, returns or stock changes online after finishing the offline session. Cash-session changes and multiple held carts are outside this offline scope.

Saved sales upload in order while the page is open, with manual synchronization available. Server validation, UUID identifiers and saved payload hashes make retries return the original receipt without repeating stock, cash or debt movements. Sale time drives expiry, cash/debt dates and reports; valid queued sales can upload after their preparation expires. Failed or rejected uploads stay visible for review. Finish session first pauses new sales, uploads every saved event, then releases the counter. An interrupted finish can be retried.

Use **Export recovery copy** regularly and keep the JSON privately; it includes receipts and customer names. Export reads state and sales in one storage transaction. **Restore recovery copy** requires online owner access and a browser with no active session or pending uploads. It validates the ordered queue and stock balances, pauses new sales, and rechecks every original upload against the server before finishing. It does not invent or recover sales absent from the copy. Preserve the original browser profile/site data until every sale is confirmed. Browser storage permission may be declined; storage loss, cleared data and a lost device still require recovery planning. There is no force-release procedure for a lost prepared browser yet.

The service worker caches only the public checkout shell and its local assets, never login pages, reports or API responses. Passwords and CSRF tokens are not stored in IndexedDB. Explicit sign-out locks the local interface across tabs; expired server authentication blocks uploads until online sign-in. Remote revocation cannot be detected while disconnected, so preparation is bounded. Offline use requires localhost or HTTPS and a browser supporting service workers/IndexedDB; Android network/HTTPS access and actual-device acceptance remain pending. Mobile presents an analytics link only.

## Shared records and import

`PosStore` adapts the existing business services to Laravel Query Builder storage. The POS migration adds 28 tables for products/options, batches and movements, suppliers/orders/deliveries/bills/payments, customers/debts/repayments, sales/returns, cash sessions/movements, expenses and workspace initialization. Core identifiers, quantities, money and references have typed columns; JSONB snapshots retain detailed historic values. Sale, return, order and bill lines are stored separately. Money uses exact integer minor units and stock uses whole base units.

Connected browser sessions read the same shop records. Refresh a page to see changes made elsewhere; live cross-device updates remain pending. Offline checkout synchronizes through the same transaction rules. Android/network deployment has not been configured or accepted yet.

Each authenticated business web request and standalone business mutation takes the shop workspace row lock before reading mutable records. Related stock, debt, cash and receipt changes commit in one database transaction. Unique document/event identifiers, foreign keys, SKU/barcode uniqueness, quantity constraints and one-open-cash-session enforcement provide additional safeguards. The shop lock serializes connected operations for this single-shop version; this is not a high-throughput architecture. Existing collection-based services currently read and upsert their complete collections.

A new uninitialized workspace presents an import review before business writes are allowed. The owner selected the records currently visible in the browser. The completed local import contains Bottled drink (72 bottles) and Instant noodles (48 packets), their five sale options and matching unknown-expiry legacy batches; no sales, returns or debts were present. No financial test entries were added to these records. Other browser snapshots are archived separately and never silently merged. `php artisan pos:archive-sessions` preserves available file-session demo data in private `storage/app/private/pos-imports` JSON archives. Import also archives its source and effective catalogue, preserves saved historical values, validates batch balances, and rejects a second initialization. These archives are import safeguards, not scheduled database backups.

## Working behavior

Products support creation/editing, selling prices, optional purchase cost per base unit, package options, unique SKUs/barcodes, reorder thresholds and opening-stock expiry. Existing package conversions must be retained. Prices/costs accept at most two decimal places. Stock counts require a reason and preserve before/after quantities, differences and batch movements. Placeholder images appear in catalogue, checkout and cart; real image management is deferred.

Checkout supports name/SKU search, manual barcode entry on Enter, repeated scans, individual/package quantities, removal, cash/change, grocery credit and manually confirmed GCash/Maya payments. The payment QR is printed from the payment app and displayed at the counter. The system records confirmed payments; it does not transfer money. Completion requires an open cash session, aggregates base-unit deductions, blocks insufficient sellable stock and saves an immutable numbered receipt. Duplicate submission identifiers return the existing event. Transactions offers receipt/product/customer/date search, period/payment/return-status filters, COPY reprints and browser Print/Save PDF. Physical printer integration remains pending.

Stock is tracked per opening/delivery batch with original quantity, source, expiry and full-batch acquisition cost snapshots. Sales consume earliest expiry first, then undated stock, using oldest receipts for equal expiry. Known expired batches are excluded from checkout; an expiry date remains sellable through that Asia/Shanghai calendar day. Inventory filters show expired, due within 30 days, unknown-expiry and depleted batches with linked movement history. Legacy stock remains undated with unknown acquisition cost rather than reconstructing old deliveries. Batch quantities must reconcile with product stock before a mutation commits.

Purchasing supports supplier creation/editing, multi-line orders, expected-cost snapshots and partial/full receiving at actual cost and expiry. Whole delivery validation, stock updates, batches and supplier bills commit together. Each purchase-order delivery creates a separate unpaid bill; orders alone do not create debt. Optional invoice references and due dates, outstanding/overdue totals, filters and bill lines are available. Separate partial/full Cash, GCash and Maya payments preserve references, balances, timestamps and cash links. Digital payments require an app reference; cash payments require an open drawer with enough expected cash. Direct Inventory receiving updates stock/history but does not create supplier bills. No orders are sent to suppliers. Opening supplier balances, corrections and supplier returns remain pending.

Customer Credit & Loans supports customers, linked grocery-credit sales, recorded cash-loan principal, optional due dates and partial/full repayments. Repayments reduce debt without creating sales or deducting stock; overpayment is blocked. Loans record money already lent and do not execute transfers. Interest, debt corrections and write-offs remain pending.

Stock Losses records unpaid consumption, damage, expiry, missing stock and other losses with reasons/notes, individual/package quantities and before/after stock. A selected batch or automatic FEFO allocation is supported, including expired stock. Recorded batch costs are used automatically. Optional manual acquisition-cost estimates apply only to unknown-cost units and never replace a known batch cost; the basis is labeled in history. Omitted unknown costs remain null and a recorded zero remains known. Losses create neither sales nor customer debt.

Returns preserve original sale-option quantities, selling prices and saved costs. Sellable returns restore their original batches/expiry; discarded returns create one linked loss without another stock deduction. Credit returns reduce outstanding grocery debt first and refund only paid excess. Confirmed cash/digital refunds require an open cash session; cash cannot overdraw the drawer. Duplicate and excess returns are blocked. Legacy receipt returns become undated batches. Original receipts and closed cash summaries remain unchanged.

Shifts & Expenses supports one open cash session, opening float, reasoned additions/withdrawals, paid expenses, closing counts and signed shortage/surplus with explanatory notes. Sales, cash loans, repayments, refunds, supplier payments and expenses create linked movements atomically. Cash sales contribute the total after change; grocery credit adds no drawer money. Digital records outside a session remain unassigned. Closed summaries are preserved and printable. Forms bound to an older/closed session must be reloaded.

Dashboard/Reports include daily sales/collections graphs and tables, payment breakdowns, top products, customer/supplier balances and overdue amounts, loans, low stock, expiry alerts, stock-loss reasons, paid-expense categories and drawer differences. Filters cover the last 7/30/90 local days; current stock and balances are all-time/current. Repayments are collections; loans and supplier payments are excluded from sales. Supplier payments do not create another stock expense.

New sale costs use acquisition costs of allocated stock batches, following the existing expiry-first order. Partial returns reverse the exact original allocation, including mixed batches and fractional cents; restored stock retains its value for resale. Losses use affected batch costs, with separately labeled manual estimates only for unknown units. Editing the product default cost does not revalue batches or receipts. New opening stock captures its entered unit cost; direct and purchase-order deliveries capture actual full-batch cost. Older receipts retain their saved cost basis and are never recalculated.

Cost allocation uses integer cents and cumulative proportional shares, so a cost of 1.00 over three base units allocates 0.33, 0.33 and 0.34. Saved cost segments preserve these shares through partial returns, discard and resale; total allocation equals original cost. Existing partially depleted costed batches without segments start from the proportional unsold remainder; historic transactions are untouched. Legacy returns without original cost segments restore unknown-cost stock rather than inventing an actual cost. Count decreases remove allocated stock value and count increases remain unknown; counts do not create operating expenses.

Dashboard/Reports show estimated cost of goods, gross profit/margin, operating profit and product profit using saved costs. Missing costs withhold affected totals; zero and negative profit are supported. Paid expenses and valued losses reduce operating profit; known portions of incomplete losses are disclosed. Inventory shows remaining batch acquisition value. Reports show current known stock value and units with unknown cost, withholding total valuation when incomplete. Transactions provides a saved acquisition-cost breakdown outside the printable customer receipt. Taxes and unrecorded costs remain excluded.
